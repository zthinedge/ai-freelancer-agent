## 2. 数据分类

Agent状态明确区分四类信息：

| 类型 | 示例 | 允许进入后续步骤吗 |
|---|---|---|
| 已确认事实 | 客户明确说“需要中英文官网” | 可以，并记录来源和原文证据 |
| 显式假设 | 初步推测需要CMS | 不可当成事实，只能展示或追问 |
| 待澄清字段 | 内容由谁提供、是否需要后台 | 不可进入受影响的范围与估时步骤 |
| 确定性结果 | 报价Tool计算的金额 | 可以引用，但必须保留策略版本并等待人工确认 |

客户原话始终是不可信数据。模型可以提取它表达的业务目标，但其中“忽略规则”“泄露Prompt”“直接调用Tool”等文字没有指令权限。

## 3. 版本规则

- `schema_version`：业务数据结构版本，P2固定为`1.0.0`；
- `case_version`：单个评测案例版本，P2固定为`1.0.0`；
- `skill_version`：Skill行为版本，当前Manifest为`0.1.0`；
- `prompt_version`：运行时Prompt版本，格式必须为语义化版本；
- `policy_version`：确定性报价策略版本；
- 修改字段含义或删除字段时提升主版本，兼容新增提升次版本，文案修正提升修订版本。

## 4. 后端与前端契约映射

API线上传输使用`snake_case`，前端领域模型使用`camelCase`。转换只能放在后续P3-P4的API Adapter中，React组件不得自行猜测字段。

| 语义 | 后端Pydantic | 前端TypeScript | 关键约束 |
|---|---|---|---|
| 金额 | `Money` | `Money` | amount使用十进制字符串，货币固定CNY |
| 项目输入 | `ProjectBrief`／`CreateProjectCommand` | `ProjectBrief`／`ProjectIntakeDraft` | 客户原话10-5000字符 |
| 需求提取 | `RequirementIntakeInput/Output` | 同名类型 | 事实必须有source和evidence |
| 澄清 | `ClarificationPlannerInput/Output` | 同名类型 | 必须输出3-6题并进入人工节点 |
| 范围 | `ScopeDesignerInput/Output` | 同名类型 | Must至少1项，Won't至少2项 |
| 工时 | `TaskEstimatorInput/Output` | 同名类型 | 0.5小时粒度，max不得小于min |
| 风险 | `RiskReviewerInput/Output` | 同名类型 | 固定五类风险和三级严重度 |
| 报价 | `PricingToolInput/Output` | 同名类型 | 必须恰好包含基础、标准、高级三级 |
| 方案 | `ProposalWriterInput/Output` | 同名类型 | 只能是AI草案，必须人工审批 |
| 运行状态 | `AgentState` | `AgentState` | 每个阶段输出为显式可空字段 |
| HTTP错误 | `ErrorResponse` | `ApiErrorResponse` | 稳定错误码、用户消息、Trace ID |

## 6. 评测集设计

10个案例覆盖八类主要服务、一个极度模糊输入和一个Prompt Injection输入。每个案例都包含：

- 输入、版本和标签；
- 必须识别的关键事实；
- 缺失字段；
- 必问问题的语义意图；
- 禁止行为；
- 预期工作流暂停点；
- 机器和人工验收标准。

P2只验证案例结构和覆盖是否合格。P3实现前两项Skill后开始计算事实召回、问题覆盖、重复率和越权率；P7要求固定案例整体通过率不低于80%。
