# 接单智策产品需求文档（PRD）

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 产品名称 | 接单智策 - AI自由职业接单助手 |
| 版本 | MVP v0.2（AI Native需求草案） |
| 产品形态 | 响应式Web应用 |
| 目标周期 | 5个开发日 |
| 项目性质 | Vibe Coding课程实践项目 |
| 完成方式 | 独立完成 |

## 2. 项目背景

AI编程、建站、设计和内容服务增长迅速。自由职业者虽然可以借助AI完成交付，却常因需求澄清、范围管理、工时估算和商务报价能力不足而低价接单或反复返工。

接单智策将客户的自然语言描述转成结构化项目方案，使接单者在正式承诺前完成必要追问、范围分级、任务估时、风险检查和报价准备。

### 2.1 AI Native定位

接单智策不是在普通表单中附加一个“AI生成”按钮，而是由AI Agent驱动完整的接单分析过程：Agent理解目标、判断当前状态、选择合适的Skill、调用计算工具、检查结果，并在关键商业决策前请求人工确认。

首版采用“确定性工作流 + 受约束的主Agent”混合架构：

- 代码负责固定业务顺序、状态保存、超时重试和报价计算；
- 主Agent负责理解需求、判断缺失信息和选择需要执行的Skill；
- Skill封装可复用的专业步骤、提示词、输出结构和质量标准；
- 人类负责确认范围、工时、价格和最终对外承诺；
- 每次运行保存步骤、耗时、工具调用和结果，支持回放、调试与评测。

项目同时有两个目标，但不能混淆：产品面向自由职业者解决接单问题；Agent知识是项目开发者的学习与作品展示目标，不把“学习Agent”强加给最终用户。

## 3. 产品目标

### 3.1 核心目标

1. 让用户在5分钟内从一段模糊描述生成第一版项目方案；
2. 自动发现不少于3项缺失信息；
3. 输出Must／Should／Could／本次不做四级范围；
4. 给出可解释的任务工时和三级报价；
5. 保存项目记录，支持后续复用和演示。
6. 让用户看到Agent完成了哪些步骤、调用了哪些Skill，以及哪些内容仍需人工确认；
7. 通过真实案例评测Agent的结构完整性、稳定性和业务可用性。

### 3.2 非目标

- 不自动登录、抓取或发布闲鱼／小红书；
- 不代替律师生成具有法律效力的合同；
- 不实现在线收款、发票和资金托管；
- 不承诺报价一定准确；
- 不做多人实时协作和复杂权限系统。

## 4. 核心用户故事

### US-01 创建项目

作为自由职业者，我想输入客户原话、预算、期限和自己的时薪，以便系统理解项目背景。

验收标准：

- 客户需求少于10个字符时不能提交；
- 预算、时薪必须为非负数；
- 提交时显示清晰的加载状态；
- API失败时展示可理解的错误信息。

### US-02 需求澄清

作为自由职业者，我想看到AI识别出的缺失信息和追问，以便在报价前向客户确认关键问题。

验收标准：

- 输出3-6个与当前项目有关的问题；
- 问题覆盖目标、范围、内容材料、期限或售后；
- 不重复用户已经明确提供的信息。

### US-03 范围拆分

作为自由职业者，我想把功能分为Must、Should、Could和本次不做，以便控制MVP边界。

验收标准：

- 四个范围均使用短句列表；
- Must至少2项；
- 本次不做至少2项；
- 生成内容允许用户后续修改（MVP可先只读，列入下一迭代）。

### US-04 工时与报价

作为自由职业者，我想看到任务拆分、预计工时和三级报价，以便向客户提供有依据的选择。

验收标准：

- 每项任务包含名称、说明和工时；
- 报价由时薪、总工时和风险系数计算；
- 展示基础版、标准版和高级版；
- 当预算明显低于建议报价时显示范围提醒；
- 页面注明报价仅供沟通参考。

### US-05 项目历史

作为自由职业者，我想查看过去分析过的项目，以便复用项目经验。

验收标准：

- 展示项目名、类型、预算、建议报价、创建时间；
- 点击项目可查看完整分析；
- 支持删除测试项目；
- 删除前需要用户确认。

### US-06 查看Agent执行过程

作为自由职业者，我想看到系统如何从原始需求得到结论，以便判断AI建议是否可信，而不是直接接受一个黑箱结果。

验收标准：

- 展示“理解需求、生成追问、规划范围、拆解任务、计算报价、风险检查”六个步骤的状态；
- 每一步显示使用的Skill、简短输入摘要、结构化结果和耗时；
- 不展示模型的隐藏思维过程，只展示可验证的操作记录和业务依据；
- Skill失败时显示失败原因、重试或降级状态；
- 报价生成后必须由用户确认，确认前标记为“AI草案”。

### US-07 补充信息后继续运行

作为自由职业者，我想回答AI提出的澄清问题后继续同一个项目，而不是重新填写全部内容。

验收标准：

- 保存当前项目状态和待回答问题；
- 用户补充答案后，从范围规划节点继续执行；
- 新结果能够引用补充信息，并标识相较上一版发生的变化；
- 重复提交不会产生两份相同报价记录。

## 5. 功能优先级

| 优先级 | 功能 |
|---|---|
| Must | 新建项目、主Agent编排、6个核心Skill、结构化分析、澄清问题、范围拆分、任务估时、确定性三级报价、风险检查、人工确认、项目与运行记录 |
| Should | Agent步骤面板、补充回答后继续运行、规则降级、Markdown复制、预算不足提醒、10个案例评测集、移动端适配 |
| Could | PDF导出、报价模板、项目搜索筛选、MCP工具接入、质量评审Agent、真实用户反馈入口 |
| Won't | 支付、电子合同、平台自动发布、多租户权限、实时协作、自主联系客户、无人工确认的自动报价、多Agent自治团队 |

## 6. Agent工作流与Skill编排

### 6.1 核心概念

| 概念 | 在本项目中的含义 |
|---|---|
| Agent | 具有目标、指令、状态和工具使用能力的任务执行者 |
| Workflow | 由代码约束的业务步骤、分支、重试和人工确认流程 |
| Skill | 针对单一业务能力的可复用说明、输入输出契约、参考资料和测试用例 |
| Tool | Agent可调用的确定性函数或外部服务，例如报价计算和项目查询 |
| Memory／State | 当前项目事实、澄清答案、运行节点和历史版本，不等同于无限保存聊天记录 |
| Guardrail | 对输入、工具调用和输出进行格式、安全、隐私与业务规则校验 |
| Trace | 一次运行中模型调用、Skill选择、工具调用、耗时和错误的可观察记录 |

### 6.2 MVP Agent组成

首版只设置一个面向用户的“接单策略Agent”，由它持有上下文并编排以下Skill：

| Skill | 职责 | 主要输入 | 结构化输出 |
|---|---|---|---|
| `requirement_intake` | 提取客户目标、用户、交付物、预算、期限和约束 | 客户原话 | 已知事实、未知项、项目类型 |
| `clarification_planner` | 根据未知项生成有优先级的追问 | 已知事实、未知项 | 3-6个问题及提问理由 |
| `scope_designer` | 建立MoSCoW范围和排除项 | 已确认事实、澄清答案 | Must／Should／Could／Won't |
| `task_estimator` | 拆解任务、依赖和工时区间 | 项目范围、交付标准 | WBS、工时、依赖 |
| `risk_reviewer` | 检查技术、需求、进度和商务风险 | 范围、任务、客户约束 | 风险等级、原因、措施 |
| `proposal_writer` | 将已确认结果整理为客户可读方案 | 全部结构化结果 | 报价说明、交付范围、验收条件 |

报价不是生成式Skill。`pricing_calculator`是确定性Tool，按时薪、工时、复杂度、风险系数和服务范围计算金额，Agent只能解释结果，不能绕过公式自行填写价格。

### 6.3 编排流程

```text
输入客户原话
  -> 输入Guardrail：长度、敏感信息和Prompt Injection提示
  -> requirement_intake
  -> clarification_planner
  -> 人工节点A：用户补充或确认关键信息
  -> scope_designer
  -> task_estimator
  -> risk_reviewer
  -> pricing_calculator Tool
  -> proposal_writer
  -> 输出Guardrail：字段、金额、排除项和免责声明检查
  -> 人工节点B：用户确认范围与报价
  -> 保存项目、AgentRun、Trace和最终方案
```

当信息不足时，Agent必须暂停并等待用户补充；当模型、Skill或外部服务失败时，工作流可从最近节点重试，或降级为规则模板。MVP不允许Agent自动向客户发送消息或自主承诺价格。

### 6.4 Skill契约

每个Skill必须具备：名称与用途、触发条件、禁止使用条件、输入Schema、输出Schema、可调用Tool、异常处理、至少3个评测案例。Skill之间只传递结构化状态，避免依赖不可验证的长文本。

建议在实现阶段使用独立目录管理Skill：

```text
skills/
  requirement_intake/SKILL.md
  clarification_planner/SKILL.md
  scope_designer/SKILL.md
  task_estimator/SKILL.md
  risk_reviewer/SKILL.md
  proposal_writer/SKILL.md
```

### 6.5 为什么MVP不直接做多Agent

当前六个步骤共享同一份项目状态，最终由同一用户确认，使用单个主Agent更容易控制成本、延迟、调试和评测。后续只有在专业Skill需要独立上下文、独立权限或并行执行时，才把某个Skill升级为专家Agent。多Agent是扩展手段，不是AI Native的必要条件。

## 9. 非功能需求

- 首屏在普通电脑上2秒内可交互；
- 规则模式单次分析响应小于1秒；
- 大模型请求超时15秒后自动降级规则模式；
- 不在前端保存API密钥；
- 输入长度限制5000字符；
- 核心API测试覆盖率目标70%以上；
- 375px宽度下核心流程可正常操作；
- 表单具有label、焦点状态和键盘可操作性。
- Agent输出必须通过Schema校验，不合格时最多自动修复1次；
- 所有Tool使用白名单和明确参数Schema，涉及外部写操作时必须人工批准；
- Agent运行支持幂等键、超时、有限重试和从节点恢复；
- Trace默认不记录API密钥和完整敏感原文；
- 为模型调用记录延迟、Token、估算成本、失败原因和降级比例；
- Prompt、Skill和评测集需要版本号，保证结果可复现和对比。

## 10. 成功指标

| 指标 | MVP目标 |
|---|---:|
| 完成一次方案生成的成功率 | ≥95% |
| 从录入到结果展示的完成时间 | ≤5分钟 |
| 每个项目发现缺失问题数 | ≥3 |
| 3名测试用户认为结果“有帮助” | ≥2人 |
| 与手工整理相比时间下降 | ≥50% |
| Agent工作流完整执行率 | ≥90% |
| Skill结构化输出Schema通过率 | ≥95% |
| 报价金额与确定性公式一致率 | 100% |
| 高风险报价经过人工确认 | 100% |
| 10个固定案例回归评测通过率 | ≥80% |

## 11. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| AI结果不稳定 | 输出难演示 | JSON约束、服务端校验、规则回退 |
| 报价被误认为承诺 | 商务纠纷 | 展示计算依据和免责声明 |
| 客户内容包含敏感信息 | 隐私风险 | 提示脱敏、限制日志内容 |
| 功能范围过大 | 无法一周交付 | 坚持Must范围，导出和编辑后置 |
| 外部API不可用 | 演示失败 | 无密钥规则模式、超时降级 |
| Agent自主性过高 | 越权承诺或错误Tool调用 | Tool白名单、最小权限、人工确认 |
| Skill数量过多 | 编排复杂且难定位问题 | 首版限定6个Skill，统一契约和版本 |
| Prompt Injection | 客户文本诱导Agent忽略规则 | 客户内容按数据处理、输入Guardrail、关键操作代码校验 |
| Agent结果无法复现 | 难以调试和展示改进 | 固定评测集、Trace、版本记录和低随机性配置 |

## 12. 版本规划

### v0.1：基础可运行原型

完成输入、分析、报价、保存和历史查看闭环。

### v0.2：AI Native Agent MVP

完成主Agent、6个Skill、确定性Tool、两个人工节点、运行状态、Trace和10个案例评测集。

### v0.3：Agent工程能力扩展

根据3名用户反馈加入Skill版本管理、质量评审Agent、并行风险检查，以及一个只读MCP数据源；验证确有价值后再引入专家Agent。

### v1.0：产品化

增加个人模板、报价规则、账户、多项目筛选、长期记忆治理和团队权限；是否扩展多Agent由真实业务复杂度决定。
