# AI Skill编排与差异化报价

## 1. 改造原因

旧版报价使用“服务类型固定基准工时 × 用户时薪 × 档位系数”。这种实现虽然金额可复算，但同一服务类型的简单项目和复杂项目会得到接近的价格，无法体现真实范围、任务数量、依赖和风险，只适合作为无模型时的降级方案。

当前版本将主流程改为“模型负责分析，代码负责算钱”：

```text
客户原话
  -> requirement_intake（DeepSeek API）
  -> clarification_planner（DeepSeek API）
  -> 人工回答
  -> scope_designer（DeepSeek API）
  -> task_estimator（DeepSeek API）
  -> risk_reviewer（DeepSeek API）
  -> pricing_calculator（本地确定性Tool）
  -> proposal_writer（DeepSeek API）
  -> 报价人工确认
```

## 2. Skill职责与约束

| Skill／Tool | 主要职责 | 能否生成金额 |
|---|---|---:|
| `requirement_intake` | 提取目标、类型、事实、未知项 | 否 |
| `clarification_planner` | 生成3-6个高价值澄清问题 | 否 |
| `scope_designer` | 根据事实与答案生成MoSCoW范围 | 否 |
| `task_estimator` | 按实际交付物生成WBS、依赖、最小／最大工时 | 否 |
| `risk_reviewer` | 分析需求、技术、进度、隐私和商务风险 | 否 |
| `pricing_calculator` | 使用验证后的工时、时薪和风险准备金计算价格 | 是，唯一来源 |
| `proposal_writer` | 将范围、风险和Tool报价整理成AI草案 | 否，只能复制Tool金额 |

每个模型Skill都使用独立版本化System Prompt、Pydantic输出Schema和最多一次结构化修复。初始需求提取失败时可切换规则模式生成澄清问题；用户回答后的关键Skill失败时则安全停止，不生成可批准报价，避免把不可靠降级结果包装成正式商业建议。

## 3. 工时与价格计算

### 3.1 工时来源

`task_estimator`不再接收服务类型固定总工时。它必须按具体交付物拆解3-12个左右的任务，并为每项提供：

- 任务描述与依赖；
- `min_hours`：合理顺利情况下的工时；
- `max_hours`：考虑当前已知不确定性的合理上界；
- 数量、复杂度、接口、页面、素材或修改轮次等估算依据；
- 0.5小时粒度与独立验收标准；
- 跨任务返工和集成缓冲。

软件／AI类项目的估算方法参考已审计并安装的 `Enreign/progressive-estimation`：任务拆解、三点估算思想、PERT、置信区间、不确定性锥和历史校准。该外部Skill是Codex侧的方法参考，不是产品运行时依赖；产品运行时使用仓库内的`task_estimator`契约和Prompt。

### 3.2 风险准备金

风险准备金由代码根据风险输出计算，不由模型直接填写：

```text
基础准备金 = 5%
每个风险类别只取最高严重度，重复描述不重复计价
低风险类别 = +1%
中风险类别 = +3%
高风险类别 = +5%
不确定性说明 = 每项 +1%，最多 +3%
总准备金上限 = 25%
```

风险类别固定为需求、技术、进度、隐私和商务。该规则避免模型因为输出更多文字或把同一风险拆成多条而抬高报价。

### 3.3 三级报价

```text
min_hours = 所有任务最小工时之和
max_hours = 所有任务最大工时之和 + buffer_hours
PERT_hours = (min + 4 × √(min × max) + max) ÷ 6

乐观估算 = min_hours × 时薪
推荐估算 = PERT_hours × 时薪 × (1 + 风险准备金)
保守估算 = max_hours × 时薪 × 1.10
```

三档使用同一交付范围，表达不同工时置信边界，不再伪装成范围不同的服务套餐。`max_hours`已经包含已知风险与`buffer_hours`，所以保守估算不再重复叠加风险准备金。所有工时按0.5小时取整，金额按人民币分取整。预算不会用于倒推工时，避免为了迎合客户预算而伪造工作量。

## 4. 真实API对比

2026-08-20使用相同时薪`¥150/小时`完成DeepSeek真实链路验证。下表为报价策略`1.0.0`的历史基线；策略`1.1.0`上线后需重新执行真实API校准，不能直接作为当前报价结果：

| 案例 | 服务类型 | 模型生成任务 | 工时区间（含缓冲） | 风险数 | 标准报价 |
|---|---|---:|---:|---:|---:|
| 简单单页作品集 | website | 8 | 17.5-39小时 | 5 | ¥5,103.00 |
| 复杂跨境企业门户 | website | 13 | 320-564小时 | 10 | ¥83,947.50 |

两个项目服务类型与时薪相同，报价差异来自页面数量、CMS、权限、登录、搜索、表单、数据迁移、SEO、CRM、部署和风险，而不是固定的`website`价格表。

验证结果：

- 简单案例和复杂案例均使用`execution_mode=model`；
- 报价包含基础、标准和高级三个档位；
- Proposal中的金额由服务端强制覆盖为Tool结果，模型无法篡改；
- 后端26项自动化测试通过，前端架构、类型和生产构建通过。

## 5. SkillHub与供应链边界

SkillHub存在多个同名市场，公开Skill质量和权限差异较大。本次只采用可追溯GitHub源代码、MIT许可证、无自动执行安装脚本的`progressive-estimation`作为方法参考，并安装到本机Codex Skills目录。

外部Skill不会自动进入产品后端，也不会在生产环境执行。产品内Skill必须满足：

- 代码仓库内版本化；
- 输入输出Schema可验证；
- 不包含密钥和外部写权限；
- 模型只分析，价格Tool由代码控制；
- 有固定评测案例和降级路径。

## 6. 当前限制与下一步

- 完整流程需要6次模型调用，当前真实案例耗时约38-42秒；
- 无模型或调用失败时仍会使用服务类型基准工时作为降级，不应把降级价直接对外承诺；
- 当前项目使用内存存储，无法积累“预计工时与实际工时”校准数据；
- 下一阶段应接入数据库，记录每项任务实际用时并计算估算偏差，逐步替换通用风险权重；
- 可在不破坏Skill边界的情况下合并部分模型请求或缓存中间结果，降低延迟和Token成本。
