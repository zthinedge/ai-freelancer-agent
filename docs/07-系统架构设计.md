# 接单智策系统架构设计

## 1. 架构目标

接单智策采用“可在5个开发日内完成、后续可持续扩展”的工业级模块化单体。架构首先保证边界清晰、依赖可替换、核心流程可测试，不以微服务数量或Agent数量衡量先进程度。

核心目标：

- 前后端职责分离，API是唯一通信边界；
- 业务规则不依赖FastAPI、React、SQLite或具体模型SDK；
- 模型、数据库、Trace和Tool均通过端口替换；
- Skill具有独立契约、版本和评测入口；
- 报价、审批和状态迁移由确定性代码控制；
- 支持后续接入MCP、PostgreSQL或专家Agent而不重写领域层；
- 架构规模必须服从课程的一周MVP周期。

## 2. 关键架构决策

| ADR | 决策 | 理由 | 当前代价 |
|---|---|---|---|
| ADR-001 | 模块化单体，而不是微服务 | 单人5日周期更容易开发、测试和部署；模块边界仍可独立演进 | 不能独立扩缩某个模块，MVP不需要 |
| ADR-002 | 后端采用清洁架构／端口适配器 | 隔离Web、数据库和模型供应商，方便Mock和替换 | 文件数量比脚本式项目多 |
| ADR-003 | 前端采用轻量Feature分层 | 状态和API围绕用户动作组织，避免根组件膨胀 | 需要遵守单向导入规则 |
| ADR-004 | 单主Agent + Skill Registry | 共享项目状态、成本低、容易Trace；Skill可独立测试 | 暂不展示复杂多Agent协作 |
| ADR-005 | 报价使用确定性Tool | 金额可复算、可审计，模型只能解释 | 需要显式维护价格策略 |
| ADR-006 | HTTP业务API使用`/api/v1` | 为后续协议演进保留兼容空间 | MVP多一层路由前缀 |
| ADR-007 | SQLite作为MVP存储 | 零外部依赖，适合演示和本地测试 | 团队并发和扩展能力有限 |

## 3. 系统上下文

```text
自由职业者
   |
   | 浏览器操作、人工确认
   v
接单智策 Web + API
   |          |           |
   |          |           `--> Trace / Eval（可观察与评测）
   |          `--------------> SQLite（项目与运行状态）
   `-------------------------> OpenAI兼容模型API（可替换）
```

客户不是系统直接操作者。MVP不自动登录闲鱼／小红书、不自动发送消息、不代替用户承诺价格。

## 4. 容器架构

```text
┌──────────────── React + TypeScript ────────────────┐
│ app -> pages -> features -> entities -> shared     │
└───────────────────────┬────────────────────────────┘
                        │ JSON / REST
┌───────────────────────▼────────────────────────────┐
│ FastAPI Presentation                              │
│        -> Application Use Cases                   │
│             -> Agent Orchestrator + Skills        │
│                  -> Domain                        │
│        <- Ports <- Infrastructure Adapters        │
└──────────┬────────────────┬────────────────┬───────┘
           │                │                │
        SQLite       Model Gateway       Trace Sink
```

部署时仍是一个前端静态站点和一个后端进程，符合课程时间和演示成本；内部边界不依赖部署数量。

## 5. 后端架构

### 5.1 目录结构

```text
backend/app/
├─ domain/                 纯领域实体、枚举和值对象
├─ application/            用例契约、命令、查询和外部端口
├─ agent/                  Agent状态、编排端口、工作流与Skill清单
│  └─ skills/              六个版本化SKILL.md
├─ infrastructure/         AI、存储、Trace和Tool适配器插槽
├─ presentation/http/      FastAPI路由、请求响应与错误映射
├─ bootstrap/              Composition Root和应用工厂
├─ core/                   配置与跨模块错误
└─ main.py                 进程入口
```

### 5.2 依赖规则

```text
domain
  ↑
application   agent
  ↑             ↑
infrastructure  presentation
       \        /
        bootstrap
```

必须遵守：

- `domain`不导入FastAPI、Pydantic、数据库或模型SDK；
- `application`和`agent`只依赖领域与抽象端口；
- `presentation`调用用例，不直接调用SQLite或模型客户端；
- `infrastructure`实现端口，不反向定义业务规则；
- 只有`bootstrap`知道具体适配器并完成依赖注入；
- 依赖规则由`tests/test_architecture.py`自动检查。

### 5.3 后端模块职责

| 模块 | 可以做 | 不可以做 |
|---|---|---|
| Domain | 定义Project、AgentRun、状态枚举和业务不变量 | 访问网络、数据库、环境变量 |
| Application | 定义创建项目、补充答案、确认报价等用例 | 知道SQLite表结构或HTTP状态码 |
| Agent | 决定Skill契约、工作流顺序、Tool边界 | 直接读取密钥、直接写数据库 |
| Infrastructure | 调用模型、持久化、记录Trace、执行报价工具 | 修改业务流程或跳过审批 |
| Presentation | 校验HTTP输入、调用用例、映射响应 | 编写业务规则或直接实例化SDK |
| Bootstrap | 创建配置、适配器和容器 | 承载业务逻辑 |

## 6. Agent与Skill架构

### 6.1 主工作流

```text
Input Guardrail
  -> requirement_intake
  -> clarification_planner
  -> Human Checkpoint A
  -> scope_designer
  -> task_estimator
  -> risk_reviewer
  -> pricing_calculator Tool
  -> proposal_writer
  -> Output Guardrail
  -> Human Checkpoint B
```

主Agent只负责编排和状态推进。Skill负责一个明确的专业步骤；Tool负责可确定执行；Repository负责持久化；TraceSink负责观测。四者通过Protocol解耦。

### 6.2 Skill扩展机制

每个Skill目录必须具有`SKILL.md`，包含：

- 稳定名称与语义化版本；
- 使用场景和禁止使用条件；
- 输入、输出和Guardrail；
- 允许调用的Tool；
- 评测案例要求。

新增Skill的标准流程：先新增评测案例和契约，再实现Skill，最后注册到`SkillRegistry`。不得在路由或主Agent中硬编码供应商Prompt。

### 6.3 未来升级为多Agent的条件

只有当某个Skill需要独立知识库、独立权限、不同模型或可量化的并行收益时，才升级为专家Agent。升级后继续实现同一个应用端口，调用方不感知内部是Skill还是Agent。

## 7. 前端架构

### 7.1 目录结构

```text
frontend/src/
├─ app/                    应用入口、全局Provider和样式
├─ pages/                  页面组合
├─ features/               项目录入、Agent运行、报价确认等用户动作
├─ entities/               Project、AgentRun、SkillExecution稳定类型
└─ shared/                 HTTP、配置和通用UI契约
```

### 7.2 依赖规则

```text
app -> pages -> features -> entities -> shared
```

- 下层不能导入上层；
- Feature之间不得直接互相导入；
- API访问通过Gateway接口注入；
- 服务端`snake_case`到前端领域模型的转换放在适配器；
- 页面只组合Feature，不保存领域规则；
- Agent轮询、流式事件和审批状态后续集中在`agent-run` Feature中。

## 8. API边界

| 方法 | 路径 | 对应用例 | 实现阶段 |
|---|---|---|---|
| GET | `/api/health` | 健康检查 | P1，已提供 |
| POST | `/api/v1/projects` | 创建项目并启动AgentRun | P3 |
| GET | `/api/v1/projects` | 查询项目 | P4 |
| GET | `/api/v1/projects/{id}` | 查询项目详情 | P4 |
| GET | `/api/v1/agent-runs/{id}` | 查询运行状态与Skill记录 | P3-P4 |
| POST | `/api/v1/agent-runs/{id}/answers` | 提交澄清答案并恢复 | P6 |
| POST | `/api/v1/agent-runs/{id}/approve` | 审批范围与报价 | P6 |

API错误统一包含稳定错误码、用户可读消息和Trace ID；内部异常、模型原始响应和密钥不得返回前端。

## 9. 数据与可靠性约定

- ID统一使用UUID；
- 时间统一保存UTC，展示层再转换时区；
- 金额后端使用`Decimal`，API使用十进制字符串，禁止浮点计算报价；
- AgentRun保存当前节点和结构化状态，支持暂停与恢复；
- 写操作携带幂等键，避免重复项目和重复报价；
- 外部调用具有超时、有限重试和稳定错误分类；
- Schema、Prompt、Skill和评测集均需版本化。

## 10. 安全与可观察性

- 模型密钥只从后端环境变量读取，并使用Secret类型；
- 客户文本视为不可信数据，防止Prompt Injection；
- Tool采用白名单和最小权限；
- 报价和外部写操作必须人工确认；
- Trace记录步骤、耗时、Token、估算成本、错误与降级；
- Trace和日志默认不记录完整客户原文、密钥或敏感Tool参数。

## 11. 五日开发周期映射

| 开发日 | 架构层落地 | 业务增量 | 不做内容 |
|---|---|---|---|
| 第1日 | 当前架构骨架、契约、健康检查、构建验证 | 无业务实现 | 不接模型、不建复杂数据库 |
| 第2日 | ModelGateway、Mock、SkillRegistry、Repository适配器 | 需求提取与澄清闭环 | 不实现全部Skill |
| 第3日 | 前端Gateway和Agent状态Feature | 浏览器输入、查看追问和步骤 | 不做复杂视觉系统 |
| 第4日 | Tool、Checkpoint、Trace适配器 | 六Skill、报价与两次人工确认 | 不做MCP和多Agent |
| 第5日 | 测试、部署和观测配置 | 用户验证与课程材料 | 不增加新业务范围 |

该安排把工业规范集中在稳定边界、自动检查和可替换端口，不引入微服务、消息队列、Kubernetes或复杂事件总线。
